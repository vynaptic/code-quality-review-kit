These guidelines apply to every pull request review in this repository (human, Devin Review, Codex, Claude Code, Factory Droid or any other AI reviewer).

**Full standard:** `.agents/skills/code-quality-review/`. If your tool supports skills, load the `code-quality-review` skill and follow it; otherwise read its `SKILL.md` and `references/` files. This file is the short version: where they differ, the full standard wins, and active (uncommented) rules in `.agents/review-overrides.md` win over both.

## Precedence
User instructions > `.agents/review-overrides.md` > documented repo conventions (`AGENTS.md`, `CONTRIBUTING.md`, ADRs, linter configs) > conventions observed in the codebase (≥3 existing occurrences, no stronger competitor) > the standard's defaults. Conventions override *style* rules only; bugs, security, data-loss and performance findings, and names that lie about behaviour, are always reported.

## Priorities (in order)
0. **Learn the repository first.** Before judging, profile what the codebase already does: package layout, module boundaries, type suffixes and read verbs, exception hierarchy and translation, logging facade/declaration/placeholder style, nullability annotations, DI style, validation, mapping, test stack and naming, Javadoc expectations, formatter/linter presence. Run `python3 .agents/skills/code-quality-review/scripts/scan_conventions.py` and open 2–3 neighbouring files per changed area. Record the result as **Conventions applied** in the report.
1. **Bugs and security** — does it compile and is new code actually called; logic errors, null handling, concurrency/races, transactions, idempotency, missing timeouts, swallowed errors, money as floating point or unchecked sign, time-zone errors, injection, missing authorization, secrets/PII in logs. For logic and concurrency bugs, state the concrete input or interleaving that breaks the code; policy violations (string-built SQL, secrets in code, floats for money) need no trigger.
2. **Repository conventions (enforced, `CONV-*`)** — new code follows the established naming vocabulary, packaging, module dependency direction, exception hierarchy, logging style, nullability, DI, validation, mapping, test stack and documentation conventions. A change that matches a convention is never flagged for it; a change that introduces a second way of doing a cross-cutting thing (second logging facade, second exception root, second mapping style, bypassing the global error handler) is MAJOR. Every `CONV-*` finding cites existing code or a documented rule as evidence.
3. **Naming (enforced)**
   - Methods/functions are **action verb + noun**: `calculateInvoiceTotal`, `sendPaymentReminder`. Omit the noun only when the receiver already is it (`order.cancel()`, not `order.cancelOrder()`).
   - **The verb is a contract**: `get` = cheap, no side effects; `find` = may return empty; `fetch`/`load` = I/O; `is/has/can` = boolean; `calculate` = pure; `validate` = no mutation. A name that lies about behaviour is MAJOR and never yields to convention.
   - No vague verbs (`do`, `process`, `manage`, `perform`, `check`, `handle`) outside their idioms: `handle<Event>` for handlers, `do<Verb>` as a template-method worker behind a public `<verb>` (Spring), `check<Condition>` = throw-if-invalid when the repo uses it. Full lists: `.agents/skills/code-quality-review/assets/naming-rules.json`.
   - Types are nouns named by **stereotype and context**: `Order`, `Money`, `PlaceOrderUseCase`, `OrderRepository`, `PostgresOrderRepository`, `StripePaymentGateway`, `CachingProductCatalog`, `InsufficientFundsException`. Interfaces name a **role/capability** (`PaymentGateway`, `Clock`); implementations name their distinguishing trait (`Default*`, `Simple*`, technology, added behaviour). `I` prefix only in C#.
   - Grab-bag words are findings: `*Manager`, `*Helper`, `*Utils`, `*Data`, `*Info`, `*Impl` (unless the repo convention). Framework idioms are not: `Abstract*`, `*Support`, `*Template`/`*Operations`, `*Resolver`, `*Registrar`, `*Customizer`, resource-lifecycle `*Manager` (`TransactionManager`), single-subject static `*Utils` (`StringUtils`: final, static, stateless, no dependencies).
   - Booleans read as predicates (`isRetryable`), no boolean flag arguments, no abbreviations, units in names (`timeoutMs`), one word per concept across the codebase.
4. **Design principles (enforced)** — SOLID; DRY (knowledge, not text); KISS; YAGNI; deep modules (small interface, real implementation); Law of Demeter; Tell-Don't-Ask; Command-Query Separation; composition over inheritance; encapsulation and immutability; fail fast at boundaries; make illegal states unrepresentable (value objects over primitives); dependency rule (domain never depends on infrastructure); idempotent handlers and retries. Suggest a pattern only when its force is already present (a growing type switch → Strategy/State); flag misuse (Singleton as global state, Service Locator, speculative abstractions, deep inheritance, god services).
5. **Simplicity (no over-engineering, `OVER-*`)** — every new interface, layer, generic, pattern, option, event or wrapper must name the second case or boundary that justifies it now. Interface with one implementation and no I/O boundary, pass-through service layer, Strategy with one strategy, configuration nobody sets, home-made wrapper of a JDK/library type, hooks "for later": findings. Readability: top-down methods, guard clauses, readable streams, why-comments, soft limits (method ≈30 lines, class ≈300, params ≤4, nesting ≤3). Calibrate with: would Spring Framework / Apache maintainers merge this shape?
6. **Java / Spring quality bar (`JAVA-*`)** — minimal accessibility, `final` and immutable value types with defensive copies, preconditions with messages, static factories/builders, enums over constants; exceptions unchecked by default with one root per module, cause chained, contextual message, no swallowing, narrow catches, translated at boundaries, never log-and-rethrow; logging through the repo's facade with `{}` placeholders, throwable as last argument, correct level, no PII/entities/hot-path logs; `Optional` only as a return type; interface-typed, unmodifiable collections; JUC over `synchronized`, configured executors; constructor injection, `@Transactional` on the service layer without self-invocation, no business logic or repository calls in controllers, DTOs at the boundary, `@ConfigurationProperties`, no `FetchType.EAGER`, after-commit events, configured HTTP clients with timeouts, global error handler, test slices; Javadoc on public library API; features matching the compiler baseline.
7. **Tests** — new behaviour and bug fixes are covered with the repo's stack and naming; tests are deterministic, assert outcomes, and read as specifications.

## How to report
- Each finding: `[SEVERITY][RULE-ID] path:line — problem → concrete fix`. Rule IDs come from the full standard (e.g. `BUG-CONCURRENCY`, `CONV-LOG`, `NAME-M2`, `SOLID-DIP`, `OVER-INTERFACE`, `JAVA-EXC-SWALLOW`).
- Severities: **BLOCKER** (wrong behaviour, security, data loss, breaking change, does not build) · **MAJOR** (risky/costly next change, misleading name, domain→infrastructure dependency, second parallel convention, bypassed global mechanism, missing tests) · **MINOR** (rule or convention violation without immediate risk) · **NIT**.
- Naming and convention findings default to MINOR; MAJOR when the name misrepresents behaviour, the change adds a parallel way for a cross-cutting concern, or the identifier is part of a public API (consumed outside its module/service: library/SDK, REST/gRPC/GraphQL contract, event schema, cross-team interface — not merely a `public` modifier).
- One issue, several rules: list all rule IDs and use the highest severity. Grade combined issues by combined impact (leak + swallowed error = silent data loss).
- Every report has a **Conventions applied** section (which repo conventions were enforced, and which defaults were *not* applied because the repo does it differently).
- Do not comment on what the formatter/linter already enforces. Do not post taste comments without a concrete cost. Do not flag anything the repository does deliberately and consistently.
- Verdict: REQUEST CHANGES for any BLOCKER/MAJOR; APPROVE WITH COMMENTS when only MINOR/NIT remain (each MINOR fixed or waived with a reason before merge); APPROVE when there are no findings.
